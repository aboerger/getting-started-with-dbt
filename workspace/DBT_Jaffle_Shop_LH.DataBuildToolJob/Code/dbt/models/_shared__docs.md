{#
    Doc blocks: descriptions that live in Markdown and are attached to models by name.

    A `description:` in a .yml file is fine for a sentence, but it is a poor place for a paragraph, a
    table, or an explanation that applies to the same column in four different models. So dbt lets a
    description live here instead, in a named block, and be pulled into any number of .yml files:

        description: "{{ doc('customer_type') }}"

    One definition, many references, full Markdown, and the documentation site renders it properly.
    dbt finds this file because it is under `model-paths`; the file name is arbitrary, and the
    `_<scope>__docs.md` convention just sorts it to the top of the folder.

    Blocks defined here and where they are used:
      customer_type   -> marts/customers.yml
      money_in_usd    -> staging/stg_orders.yml, marts/orders.yml
      boolean_flag    -> staging/stg_products.yml, marts/products.yml, marts/order_items.yml
      surrogate_key   -> marts/supplies.yml

    Not every description should move here. A one-line description is easier to review next to the
    column it describes; these four earn a block because they are shared, or because they need more
    than a line.
#}

{% docs customer_type %}

Whether this customer has ordered more than once, as of the last build.

| Value | Meaning | Count in the demo data |
| --- | --- | ---: |
| `new` | exactly one order ever placed | 6 |
| `returning` | two or more orders | 929 |

Derived in `customers.sql` from `count(distinct order_id) > 1`, not stored anywhere upstream — which
is the point of a mart: the definition of "returning customer" is written down once, in version
control, and every report that uses it gets the same answer.

Only six customers are `new` because a year of Jaffle Shop data is mostly regulars. The
`accepted_values` test on this column means a typo such as `'Returning'` fails the build rather than
quietly splitting a Power BI slicer in two.

{% enddocs %}


{% docs money_in_usd %}

A money amount in **US dollars**, as `numeric(16, 2)` on T-SQL or `decimal(16, 2)` on Spark.

The source system stores money as an integer number of cents, which is the right way to store money
and the wrong way to report it. The staging layer converts it with the `cents_to_dollars` macro and
keeps both forms — `subtotal_cents` alongside `subtotal` — so that a reconciliation against the source
system is always possible.

Two details behind the conversion, both worth knowing if you write the equivalent yourself:

- Dividing by `100.0` rather than `100` matters, because T-SQL would otherwise do integer division and
  silently truncate every amount.
- The type name differs per engine, so the cast is generated by a macro rather than written in the
  model. See `macros/cents_to_dollars.sql`.

{% enddocs %}


{% docs boolean_flag %}

A true/false flag, encoded to suit the engine: a `bit` (`1` / `0`) on Fabric Warehouse and Fabric SQL
database, a real `boolean` on the Fabric Lakehouse.

T-SQL has no boolean type, and cannot even put a boolean expression in a `select` list, so this
project generates the column through the `to_bool` macro and reads it back through `is_true`. The
model files themselves stay dialect-free — that portability is what Demo 4 demonstrates.

When querying these columns by hand, mind the engine: `where is_food_item = 1` on the Warehouse,
`where is_food_item` on the Lakehouse.

{% enddocs %}


{% docs surrogate_key %}

A **surrogate key**: a single value hashed from the columns that together identify a row, generated
because the source system provides no single unique column.

`raw_supplies` has one row per supply *per product*, so neither `id` nor `sku` is unique on its own.
`stg_supplies` builds the key with a macro from the dbt_utils package:

    {% raw %}{{ dbt_utils.generate_surrogate_key(['id', 'sku']) }}{% endraw %}

which compiles to an MD5 hash of the two columns, with nulls handled consistently, in whichever
dialect the target speaks. Having one key column means `unique` and `not_null` tests can guard the
grain of the table, and anything joining to it has one predictable column to join on.

{% enddocs %}
